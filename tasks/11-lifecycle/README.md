# Тема 11: Жизненный цикл Entity

## Чему учит тема
- Состояния сущности: **Transient → Persistent → Detached / Removed** и границы между ними (Persistent существует только внутри транзакции).
- **Dirty checking**: изменение managed-сущности без явного save — UPDATE генерируется при flush (конец транзакции), `@Version` растёт.
- **save vs persist vs merge**: `save(new)` → persist; `em.persist` только для transient; `em.merge` — универсально (transient → INSERT, detached → UPDATE), всегда возвращает managed-инстанцию.
- **Identity map (первичный кэш persistence context)**: в одной транзакции — одна инстанция на id; в разных транзакциях — разные инстанции; `em.clear()` сбрасывает кэш внутри транзакции.
- **Транзакции**: commit делает данные видимыми другим транзакциям, rollback отменяет (у IDENTITY id присваивается при persist, но строка после rollback исчезает).

## Контракт реализации (общий для всех 10 заданий)

В рамках этой темы студент реализует **один сервис**, который «актёр» жизненного цикла, а тест лишь наблюдает за состоянием БД и результатами. Контракт зафиксирован тестами:

- Пакет и класс: `com.example.jpalab.service.ProductLifecycleService` — класс **уже существует** в проекте (`src/main/java`, там есть демонстрационные методы `restock`/`updatePrice`); методы темы **добавляются в этот класс**, не трогая существующие.
- Класс уже отмечен `@Service` (имя бина ровно `productLifecycleService` — тесты берут его по имени из Spring-контекста).
- Инжект: `EntityManager` (`@PersistenceContext`) и `PlatformTransactionManager` (или собранный на нём `TransactionTemplate`).
- **Каждый публичный метод выполняет свою работу в НОВОЙ транзакции с propagation `REQUIRES_NEW`** — так commit/rollback сервиса не зависят от транзакций теста, а закоммиченные данные становятся видны тесту (H2, READ COMMITTED).
- Сигнатуры методов — в файлах отдельных заданий (точно такие, как в блоках «Стартовый код»).
- Тесты: `@SpringBootTest` + `TransactionTemplate` (реальные транзакции, пакет `com.example.jpalab.tasks.t11`).

Ключевое отличие темы: актёр жизненного цикла — ваш сервис с независимыми REQUIRES_NEW-транзакциями; тест лишь наблюдает за итоговым состоянием БД (native-запросы) и семантикой identity map (поведение инстанции через `em.contains`, `==`, `em.clear()`), которое только такой сервис может показать.
