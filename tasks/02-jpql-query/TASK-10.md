# Задание 10. L1-кэш: запрос и изменённая managed-сущность
- Тема: JPQL @Query
- Difficulty: 10
- Что нужно сделать: Реализуйте в `ProductRepository` метод `List<Product> findJpqlById(@Param("id") Long id)` — JPQL-запрос «товар по id». Заранее созданный тест (TASK10Test) использует именно его, чтобы доказать семантику первого уровня кэша: сущность, полученная из JPQL, управляема; изменение её в памяти без flush делает этот же объект видимым в результате ПОВТОРНОГО запроса, хотя SQL-запрос выполняется заново; после `em.clear()` из БД загружается новый экземпляр (flush не было — значение из БД).
- Стартовый код:
```java
// com/example/jpalab/repository/ProductRepository.java

// TODO: @Query (JPQL) — SELECT товара по p.id = :id
List<Product> findJpqlById(@Param("id") Long id);
```
- Тест для проверки:
```bash
mvn -Dtest=com.example.jpalab.tasks.t02.TASK10Test#firstLevelCacheReturnsManagedInstance
```
- Критерий приёмки: Тест: первый запрос — 1 SELECT; B (повторный запрос) — тот же объект, что A (`isSameAs`), с ценой 999 из памяти; при этом ВТОРОЙ SELECT всё же выполнен (L1-кэш кэширует сущности, а не SQL); после `em.clear()` C — новый экземпляр с ценой 100 (значение из БД); в комментарии зафиксировано, что «повторный запрос вернул старые данные из БД и новые данные из памяти одновременно» — следствие работы L1-кэша.
- Подсказка (не решение): JPQL-запрос на сущность, уже находящуюся в persistence context, возвращает УПРАВЛЯЕМЫЙ экземпляр, а не копию строки.
