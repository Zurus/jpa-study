# Задание 10. L1-кэш: запрос и изменённая managed-сущность
- Тема: JPQL @Query
- Difficulty: 10
- Что нужно сделать: Тест создан заранее (TASK10Test): динамические JPQL-запросы через `EntityManager` доказывают семантику первого уровня кэша: сущность, полученная из JPQL, управляема; изменение её в памяти без flush делает этот же объект видимым в результате ПОВТОРНОГО запроса, хотя SQL-запрос выполняется заново. Сравнение с результатом после `em.clear()` — в том же тесте.
- Стартовый код:
```java
// Тест создан заранее: com.example.jpalab.tasks.t02.TASK10Test
// Шаги: сохранение товара (цена 100) -> JPQL "SELECT p FROM Product p WHERE p.id = :id" ->
//       A.setPrice(999) без flush -> повторный запрос -> B -> em.clear() -> повторный запрос -> C.
//       Сравниваются A/B/C (identity и цена) и считается число SELECT через Statistics.
```
- Тест для проверки:
```bash
mvn -Dtest=com.example.jpalab.tasks.t02.TASK10Test#firstLevelCacheReturnsManagedInstance
```
- Критерий приёмки: Тест: B — тот же самый объект, что и A (`isSameAs`), и у B цена 999 (из памяти, а не из БД); в SQL-логе при шаге 4 всё же виден ВТОРОЙ SELECT; после `em.clear()` объект C — новый экземпляр с ценой 100 (значение из БД, т.к. flush не было); в комментарии зафиксировано, что «повторный запрос вернул старые данные из БД и новые данные из памяти одновременно» — следствие работы L1-кэша.
- Подсказка (не решение): JPQL-запрос на сущность, уже находящуюся в persistence context, возвращает УПРАВЛЯЕМЫЙ экземпляр, а не копию строки.
